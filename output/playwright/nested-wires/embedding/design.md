## 1. The model and the one-way contracts

### Existing order and the defect

The current pipeline is reservation placement → construction topology → routing law → allocation → road capacity → network → projection. Nodes, section walls and port points are finalized **before** routing demand exists; only roads change afterward. `nestedSpacing.clearance=72`, side inset=64 and top inset=112 are different quantities: comparing a full street width directly with 72 is incorrect. A street's half-width must fit each adjoining space, and fans/turns need additional longitudinal space. [Source: `capability/layout/core/prototype-nested-scene.ts:28–90`; `capability/layout/core/prototype-nested-placement.ts:10–22,52–75,147–175`; `capability/layout/core/nested-road-capacity.ts:31–39,76–102`.]

Demand is the number of retained travels on a road, **summing both directions**, whereas individual ranks/counts are assigned within each direction. With pitch `p=6`, `W(r)=12+12*d(r)` and half-width `H(r)=6+6*d(r)`. Thus d=20/27/39 gives W=252/336/480 and H=126/168/240. Degree alone cannot estimate transit demand. [Source: `capability/layout/core/nested-wire-lanes.ts:23–45,59–83,87–107`; `capability/layout/core/prototype-nested-placement.ts:11–15`.]

### Proposed interface and flow

Keep the module inside Layout core. Its interface consumes immutable logical construction records and retained assignments and returns either an embedding with support evidence or a typed infeasibility witness. It must hide constraint construction/materialization from the scene orchestrator. No React, DOM, other capability, adapter, or new external solver dependency is needed. Public diagnostics, if exposed in increment A, enter through `capability/layout/contract/index.ts`; declaration-only records carry the outcomes. [Existing composition/data seams: `capability/layout/core/prototype-nested-scene.ts:1–25,74–84`; `capability/layout/core/nested-wire-lanes.ts:11–22`; `capability/layout/contract/records/nested-wires.ts:31–41`; repository import rules: `docs/standards/REPO-FOLDER-STRUCTURE.md`, “Call permissions”.]

The proposed sequence is:

1. **Reservation topology, once.** Use today's content order, grid dimensions, root row membership, ancestry, and provisional positions to construct the routing skeleton. Treat those positions as routing preference coordinates, not committed physical bounds. Preserve empty leaves and all 47/15/119 authoring identities. Root wrapping must not run again after expansion: it changes adjacency. [Source: `capability/layout/core/prototype-nested-placement.ts:52–102,182–208`; `capability/layout/core/prototype-nested-roads.ts:18–68,91–108`.]
2. **Law selection and allocation, once.** Retain gate IDs/roles/sides, terminal choices, ordered road visits, directions, bridge/turn kinds, source segment ordinals, lane order/ranks, and construction contacts. Existing provisional segments can supply this plan in the first increment, but are not final physical segments. Demand is exact for this retained plan, not a guess that will be recomputed after moving nodes. [Source: `capability/layout/core/nested-wire-routing.ts:47–120,133–195`; `capability/layout/core/nested-wire-law.ts:23–35,45–57,124–167`; `capability/layout/core/nested-wire-lanes.ts:87–107`.]
3. **Support compilation, once.** From the retained plan compute widths, per-mouth fans, turn footprints, cap extents, wall-normal approach lengths and tangential gate intervals. Emit construction-owned separation constraints with producing wire/road/contact provenance. Use all prospective pieces of an orthogonal connector, not the malformed diagonal emitted by the current clamp. This is algebra over a selected template, not trial projection or collision-driven retries. [Formula sources: `capability/layout/core/nested-lane-projection.ts:95–145,168–216,228–255,322–335`; `capability/layout/core/nested-road-capacity.ts:10–24,114–136`.]
4. **Final embedding, once.** Grow only deficient free tracks/padding, compute section sizes bottom-up, then place sections/nodes top-down in the retained order. Solve the finite ordered separation system described below; select feasible gate centers; translate all dependent anchors coherently. Node dimensions, semantic order, requests and lane pitch remain unchanged. No independent dragging of an offending node. [Current placement seam to replace: `capability/layout/core/prototype-nested-placement.ts:127–175,195–207`; current node dimensions: `capability/layout/core/prototype-road-nodes.ts:1–20`.]
5. **Materialization, once.** Produce final ports, roads, construction contact references, lane coordinates and source/target endpoints from the embedding, then run network construction and supported projection once. Demand sizing becomes a consumer of the embedding's width records; it must not enlarge a road beyond what embedding reserved. Validate every named contact still exists. [Existing finalization seams: `capability/layout/core/nested-road-capacity.ts:76–111`; `capability/layout/core/prototype-road-network.ts:217–243`; `capability/layout/core/nested-lane-projection.ts:346–401`.]

**Identity migration is required.** Current street IDs embed `at` and `start`; merging also groups by coordinate equality. Rebuilding `nestedMainRoads` after movement and looking up old IDs would lose demand, change merges and orphan contacts. Retain private logical span keys (owner, axis, grid/frame/child-boundary ordinal and merged provenance), then create one bijection to final public road IDs. Rewrite roads, contacts, wire road references and lane road references through it. Preserve old public IDs and serialization order exactly when geometry is unchanged. Do not parse numeric positions back out of IDs. Also rebind `AssignedTravel.road`, `AssignedTravel.at`, terminal points and gate-plane anchors; changing only the roads map leaves stale coordinates. [Source: `capability/layout/core/prototype-nested-roads.ts:70–108`; `capability/layout/core/prototype-road-registry.ts:14–32,56–89`; `capability/layout/core/nested-wire-lanes.ts:59–74`; `capability/layout/core/nested-lane-projection.ts:74–92,214–216,354–365`.]

**Preference freezing is an explicit design decision for ratification.** Alignment, band/quadrant choice, nearest highway and fork order read provisional coordinates today. Re-evaluating any of them on expanded coordinates could change demand and break termination. Preserve their selected logical results, even when another route would become shorter. This respects “selection precedes geometry” and “materialize retained assignments, never reroute”; it does not promise final-coordinate shortest routes. If final support cannot realize a retained choice, return infeasible, not another gate choice. [Source: `capability/layout/core/nested-wire-routing.ts:42–61`; `capability/layout/core/nested-wire-law.ts:23–35,45–57,135–148`; `capability/layout/core/nested-lane-order.ts:126–154`; `capability/layout/core/nested-lane-projection.ts:346–350`.]

### What is reserved

Use a positive straight-stem margin `m=p/4=1.5` for longitudinal separation, and retain the existing pin inset/pitch obligations. This is a proposed geometric margin derived from the current forward-stem formula, not an inspector tolerance. For a street facing a node port with population n, reserve at least `H(street)+F(n)+m` between the street center and the node face, where `F(n)=max(0,n−1)*p`; use the largest **actual** rank-dependent footprint at that contact. The existing terminal capacity bound `max(0,n−0.75)*p` already combines maximum fan depth with a quarter-pitch stem. Do not add it twice. Opposing-turn reaches use `(rank+0.25)*p` and `(rank+0.75)*p`; median bridges need two separated columns. Tangential pin fit is independent of longitudinal spacing: if the fixed node side cannot fit all pins with the retained six-unit inset, report infeasible. [Source: `capability/layout/core/nested-lane-projection.ts:116–145,199–212,228–233,327–330`; `capability/layout/core/nested-road-capacity.ts:14–18`; `capability/layout/core/nested-terminal-pins.ts:5–13`; `output/playwright/nested-wires/templates-scene/verify-templates-scene.mjs:174–256`.]

Represent each protected separation as `position(v) ≥ position(u) + required(u,v)`, with body extents and support reaches included in `required`. Orient constraints by **retained structural track order**, not by an observed illegal overlap. Equality groups represent an actual shared construction line/contact; fixed-size bodies are rigid objects with face offsets, not independently stretchable anchors. Within each section use ordered column/row tracks and child bands; enclosing section padding contains all owned supports. Between sections reserve shared world/parent tracks once, with both incident half-widths. A non-gate support must remain in its owning section and outside child sections; a gate support may traverse only its declared child/parent wall. Construction cells provide the protected neighboring bodies/walls; ancestor containment propagates through nesting. A constraint spanning multiple tracks is allowed and may force several intervening gaps to grow. [Existing structural incidence: `capability/layout/core/prototype-nested-placement.ts:52–75,153–175`; `capability/layout/core/prototype-nested-roads.ts:36–68,141–177,185–195`; contact construction: `capability/layout/core/prototype-road-registry.ts:44–89`.]

Compile a finite constraint graph, collapse admitted equalities, and topologically sort it. Reject any residual cyclic dependency or unsupported nonlocal contact; do not assume the constraint graph is a DAG merely because the **import graph** is acyclic. For an admitted DAG, process each vertex once with `new(v)=max(old(v), max(new(u)+required(u,v)))`. Bottom-up child extents and top-down translations are part of this ordered computation. A final linear replay verifies every constraint, rigid dimension, contact and support membership before emitting geometry. This is a sufficient construction for the admitted structural regime, **not a proof that the real scene's full constraint graph will be admitted**; increment A must establish that before geometry work is authorized. [Motivation for explicit contact preservation: `capability/layout/core/prototype-road-registry.ts:34–42,65–89`; existing no-feedback placement contract: `capability/layout/core/prototype-nested-placement.ts:1,94–102`.]

## 2. Termination argument

Let N be the finite number of semantic nodes/sections, T retained travels, C retained contact incidences, G gates, and V/E the vertices/edges of the support constraint graph. The input section tree is finite; invalid ancestry/cyclic constraints are rejected rather than recursively repaired. Existing routing is a finite traversal of the boundary list and finite gate candidates. [Source: `capability/layout/core/nested-wire-routing.ts:25–40,88–105,133–149`; `capability/layout/core/prototype-nested-placement.ts:52–75`.]

The argument is:

1. Routing/allocation run exactly once on the reservation skeleton. They produce finite T, C and G. All road populations, ranks, turn kinds and preferred gate identities are then immutable. Width is a function only of that frozen population. [Source: `capability/layout/core/nested-wire-lanes.ts:87–107`; `capability/layout/core/prototype-nested-placement.ts:13–15`.]
2. Support construction enumerates each retained travel/transition and construction incidence a bounded number of times. It adds no new route choices or road visits. Sorting and topological admission terminate on finite V/E; a cycle yields a typed failure.
3. The admitted graph has a topological order. When processing vertex v, every predecessor is final; therefore its maximum is computed once. Each edge is relaxed once, and each vertex is finalized once. V−processed strictly decreases. No moved position can change a width, rank, graph edge or predecessor.
4. Gate interval processing visits each gate in a fixed side order once (with one backward feasibility bound pass if multiple mouths share a side), then materialization, network construction, projection and validation each run once. Failure returns immediately. It cannot re-enter routing, allocation, support compilation or placement.

Thus this proposal has **one provisional reservation placement and one final embedding**, not an unbounded width→position→width loop. The added placement work is bounded by support construction, sorting and O(V+E) graph processing. Existing lane sorting and junction processing retain their existing costs; this is not a claim that the entire builder is linear. No “try until legal”, width doubling, solver retry, or second candidate is permitted. Finite termination includes explicit infeasibility; successful admission of the authoring fixture remains a build gate. [Existing single-pass contracts: `capability/layout/core/prototype-nested-scene.ts:28–30,74–84`; `capability/layout/core/nested-road-capacity.ts:73–75`; `capability/layout/core/nested-lane-projection.ts:189–191,346–350`.]

Measurement declarations currently enumerate stages in `capability/layout/contract/records/road-prototype.ts:37–50`; they do not enforce single execution by type. A future change must expose distinct reservation/support/embedding/materialization stages, each called once, and update the operation meter transparently. Calling `nodes`, `topology`, `wire:*` or allocation twice under the same name would violate the intended contract and conceal cost. The proposal preserves the one-way semantic dependency and requires ratification of these additional named stages.

## 3. Gate intervals, consumption and infeasibility

A gate remains the same semantic port ID, role, side and child/parent ownership. Its **admissible interval** is a closed tangential range for the _center of the whole gate bundle_. The assigned crossing for wire i remains `center + lane.offset[i]` on the exact wall plane. An interval is not permission to cross anywhere along a wall. Keep four distinct mouth identities, including the evaluation mode where two entries share the left side. [Source: `capability/layout/core/prototype-nested-placement.ts:104–125`; `capability/layout/core/nested-wire-inspection.ts:75–110`; `capability/layout/core/nested-wire-access.ts:8–19,42–44`.]

For gate g, let `[L,U]` be its construction-owned free wall span and `[a_i,b_i]` the tangential footprint of every reserved lane/turn relative to the bundle center. Intersect:

- corner-safe wall span, eroded by the complete bundle footprint: `[max_i(L−a_i), min_i(U−b_i)]`;
- the intervals on which both declared perpendicular street contacts exist (with their final cap/turn support);
- the ordered cell interval excluding child-wall corners, node/fan supports and other mouths on that side;
- any explicit authored same-side intent bounds, if introduced by a later policy step.

The result `[lo,hi]` is paired with **normal support intervals on both sides of the wall**. A nonempty tangential interval alone does not fix the swallowed-driveway defect. Keep a straight gate-owned segment through the plane at the assigned offset; turns, including quarter-pitch displacement, must lie wholly beyond that segment. For the mouths-spike right-to-up example, require `streetCenter−H+p/2 ≥ wall+m`, mirrored for other sides and tightened by the selected opposing-turn ranks. Reserving the full street on its own side is stronger than this simple example, but the actual connection support must still be checked. [Source: `capability/layout/core/nested-lane-projection.ts:95–145,214–216`; `capability/layout/core/nested-road-capacity.ts:46–56`; `capability/layout/core/prototype-road-registry.ts:65–78`; ordertrial mouths-spike `design.md:79–85`.]

The logical router retains the chosen gate and a symbolic interval handle. It does not consume a final point during demand selection. After embedding, the route materializer consumes that interval: keep the desired midpoint if feasible, otherwise select its nearest feasible center deterministically. With multiple same-side mouths, freeze their identity order; a backward pass computes suffix upper bounds from required bundle separations, then a forward pass selects each nearest preference within its lower bound and suffix upper bound. This takes bounded passes and prevents an early choice consuming a later mouth's space. Disconnected feasible spans are **not** replaced by their convex hull: restrict to the retained construction cell; if that cell cannot represent one interval, return an unsupported-support witness for ratification. [Current point-only seam to change: `capability/layout/core/nested-wire-routing.ts:63–85,107–121`; `capability/layout/core/nested-wire-access.ts:8–19`; exact assigned-point observer: `capability/layout/core/nested-wire-inspection.ts:75–110`.]

`lo>hi`, exhausted normal support, insufficient pin capacity, cyclic constraints, missing contacts or invalid materialized support produce a structured failure, proposed code `infeasible-embedding`, with reason, section/port/road/wire IDs, required/available intervals and constraint provenance. The existing error union only has `unroutable-leg`; extending it is part of a ratified implementation, not something already supported. Keep the diagnostic reservation scene available with `wiring.ok=false`, following the current atomic failure pattern. Never publish partial successful wires, silently snap through a wall, switch a side, drop a gate, suppress its lane, or fall back to the illegal geometry as success. [Source: `capability/layout/contract/records/nested-wires.ts:31–41`; `capability/layout/core/prototype-nested-scene.ts:74–76`; `capability/layout/core/nested-wire-routing.ts:173–195`.]

Projection then emits the explicit gate-owned straight crossing before/after the selected supported turn. Independent inspection continues requiring exact point equality and actual corridor containment; no tolerance or acceptance-range widening is proposed. The owned-gate verifier must still see every planned traversal at its distinct offset. [Source: `capability/layout/core/nested-wire-inspection.ts:96–115`; `output/playwright/nested-wires/templates-scene/verify-templates-scene.mjs:661–693`.]

**Those changed-scene proofs have not been produced in Phase 1.** This is a design with falsifiable acceptance conditions, not permission to declare legally improved from larger padding.
