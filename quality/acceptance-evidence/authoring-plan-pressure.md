# Authoring plan pressure test

One fresh-context, bounded review of the five Authoring plan documents, the Authoring baseline contract, and the two coding-standards documents. No capability implementation was inspected. No code or plan edits were made. Findings are provisional and presumed wrong until the implementing agent verifies the counterexample against the intended contract. This is the sole plan review; no re-audit is requested.

The plan explicitly requires final domain/reference validation, scoped expected versions, atomic receipt/history writes, protected resources, hard feasibility without preview, inverse participant checks, and postcommit notification isolation. These are sufficient guard responsibilities for an injected implementation; requiring Authoring to duplicate Model/Library validation would weaken ownership. The remaining concerns are specific protocol declarations below, not objections to private module choices.

| Class | Finding and file/line evidence | Concrete counterexample | Smallest correction |
|---|---|---|---|
| major build risk | Resolved admission pins have no declared input path into the planner. `docs/specs/authoring/Doc3-Modules.md:15` declares `plan(request,snapshot)`; line 17 separately returns lease pins and promises the planner sees them. `docs/specs/authoring/Doc2-Entities-and-Invariants.md:17` defines Snapshot with only workspace, sequence, and stored records; line 31 excludes resolved alias pins from the submitted envelope fingerprint. | A request refers to a mutable preset alias. ResourceAdmission resolves and protects digest P, but the declared planner inputs contain only the unchanged submitted alias and authoritative stored snapshot. The planner cannot consume P through the declared contract; independently resolving the alias can choose Q, and inserting synthetic records into Snapshot conflicts with the prohibition on changing the authoritative snapshot. | Declare an immutable admission context argument carrying exact pins to `plan(request,snapshot,admission)`. Keep the authoritative snapshot unchanged and require proposal/candidate pins to agree with this context. Extend an existing resource/retry case with an alias that moves after acquisition. |
| major build risk | Resource release after an uncertain commit lacks a settlement guarantee. `docs/specs/authoring/Doc2-Entities-and-Invariants.md:36` releases the lease on every exit; `docs/specs/authoring/Doc3-Modules.md:14` gives Committer only Receipt/typed failure semantics, and line 48 protects resources through receipt reconciliation. Baseline `docs/baseline/02-Capabilities.md:131` requires a maintenance protocol preventing concurrent bind/deletion races. | An adapter reports a timeout while its write remains in flight. Receipt lookup returns null before that write commits; Authoring exits and releases the lease. Collection can delete the still-unreferenced blob, then the outstanding write commits its binding. Atomic record comparison and receipt uniqueness do not prevent this missing-byte commit. | State that the Committer promise settles only after its physical attempt has terminated, even when its outcome is unknown; receipt reconciliation then happens after that terminal point. If pending writes are permitted, require durable lease ownership until terminal reconciliation instead. Exercise delayed write completion within the existing commit/resource failure cases. |
| engineering violation | Valid maximum-length request IDs produce invalid internal history IDs. `docs/specs/authoring/Doc2-Entities-and-Invariants.md:14` uses checked bounded ID strings including RequestId and RecordId; `docs/specs/authoring/Doc5-Build-and-Test-Appendix.md:4` caps IDs at 160 characters. `docs/specs/authoring/Doc3-Modules.md:43` generates `tx:<request>` and `head:<original-request>` record keys. | A valid 160-character request ID makes transaction/head record IDs 163/165 characters. Every changed apply needs these records, so accepting the submitted envelope either fails at internal record validation or requires bypassing the declared ID guard. | Hash the request component when generating bounded history RecordIds, retaining the exact request ID in the transaction/head payload; alternatively declare a smaller RequestId bound that accommodates the longest prefix. Add the maximum accepted ID to an existing boundary case. |

No preference or minor findings are recorded. Review ended early within the eight-minute limit. The parent should verify these three counterexamples once, accept or reject each, and apply only necessary corrections.
