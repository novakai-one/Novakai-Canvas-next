# Host plan pressure test

12 September 2026. One bounded read-only review of application integration; the only write is this report. No implementation, tests, capability re-audit, or follow-up review. Findings are provisional and presumed incorrect until the parent verifies them.

Reviewed exactly five source targets: `docs/integration/Host-Build-Plan.md` and baseline `01-Functionality.md`, `03-Repository.md`, `05-UI-UX.md`, `06-Design-Tokens.md`. Repository AGENTS.md was read for governing instructions. Public capability implementations/contracts were not inspected.

| ID | Category | Concrete finding and consequence | Evidence | Smallest resolution |
|---|---|---|---|---|
| HP1 | major build risk | Production browser authentication has no executable bootstrap contract. The plan requires authentication before authoring/blob reads and distinct browser/agent credentials, but only explains credential injection for the development proxy and credential discovery for CLI. Serving the production app on the API origin does not specify how its first browser request obtains authentication. A clean installation can render the shell while every protected request fails, or an implementer can accidentally expose the installation token while filling the gap. | Host plan 34–35; baseline 01 line 24 and F17; baseline 03 295–296. | Before HTTP/web integration, freeze the production credential/session bootstrap, browser transport of authentication for fetch/blob/subscription requests, and expiry/restart recovery. Include a clean-start production browser operation in the already-authorized operational evidence; extend retained transport case 4 if useful, without increasing the test count. |
| HP2 | major build risk | Verified restore does not define the service handover contract. Verification and preserving the old directory are specified, but stopping admissions, draining/settling in-flight commits and resource leases, retiring old render/subscription jobs, switching live owners, and invalidating client versions/pending requests are unspecified. A restore can otherwise return successfully while an old request commits into the previous workspace, or an old scene/pending request is interpreted against the restored workspace. Ordinary revision reconciliation is insufficient unless workspace identity/generation across restore is explicitly guaranteed. | Host plan 31–32, 39–41, 50; baseline 01 F23/F26/F48; baseline 05 128–130, 138; baseline 03 286. | Specify an explicit prepare/quiesce/switch/reconnect lifecycle and its failure outcome, including an identity/generation rule for snapshots, receipts, workers and browser-local drafts. Add a restore-with-pending-request operational scenario under acceptance unit 7, reusing existing cases where needed. |

No demonstrated engineering violation or impossible capability assumption was found within these five targets. The plan explicitly inherits the baseline, so abbreviated feature lists and omitted repeated U/T acceptance details were not treated as scope deletion. The eight-case budget is preserved. These findings identify decisions to freeze before dependent host work, not established defects in built capabilities.
